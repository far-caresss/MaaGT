# 公会协力讨伐 · 自动作战设计方案

> 本文档为设计说明（不含代码实现细节），坐标基于 **720×1280（短边 720）** 实测。

## 一、目标

在「公会 → 协力讨伐」玩法中自动完成每日挑战：

1. 识别当期 4 个首领（BOSS）的属性；
2. 依据 `config/teams.json` 中配置的队伍（名字 + 属性）做最优分配；
3. 自动执行：选首领 → 选预设队伍 → 入场 → 自动战斗 → 结算 → 下一场；
4. 优先把「队伍克制 BOSS」的对先分配；次数还有剩余时，补「互不克制」的对；避免「被克」的对。

## 二、游戏规则（实测确认）

| 项目 | 内容 |
| --- | --- |
| 属性 | 火、水、土、光、暗、虚 |
| 相克环 | 火 → 土 → 水 → 火；光 → 暗 → 虚 → 光（箭头 = 前者克后者） |
| 伤害倍率 | 克制 **130%** / 互不克制 **100%** / 被克 **70%** |
| 每日次数 | **入场 3 次/天**，单场 **60 秒** |
| 英雄限制 | **每位英雄每天只能出战 1 次** |
| 目标选择 | 可自选任意首领，顺序不限 |
| 炽热模式 | 第 4 天起每天 1 个，克制伤害 **150%**（**本期不处理**） |
| 属性奖励 | 武器与英雄同属性 +10% 攻击（配队层面，机器人不处理） |

### 实测要点

1. **首领图标靠字形区分**：4 个图标都是「蓝色圆角方块 + 白色字形」，**颜色完全相同**，只能靠字形（菱形=虚 / 齿轮=光 / 山=土 / 水滴=水）。字形模板实测 IoU 0.70~0.85，次优仅 0.38。
2. **入场不做预设选择**：点击 `入场` 会**直接开打**并消耗 1 次；`演习` 不消耗次数。
3. **选择预设弹窗是自由像素滚动**：行距恒为 88，但滚动偏移**不按行吸附**（滚动后行中心变为任意值）。
   → **必须用 OCR 结果文本框的中心去点击**，不能用「第 N 行固定坐标」。
4. **弹窗列出全部预设**（含未配置的 `队伍预设1/2...`）；带**红点 = 该预设未配置完**（不可用于战斗）。
5. **`入场` 会被禁用**：当**当前选中预设**含「今日已使用」的英雄时，英雄头像显示「无法使用」，`入场` 按钮变灰不可点。
6. **每期首领都不同**：首领的**名字与形象每期都会变** → **禁止依赖首领名字**（不 OCR 名字、不写死名字），一律用「属性图标外接框 + (120, 54)」推算点击点。
7. **属性图标外接框 ≈ 48×48**：4 个槽位位置固定，但点击点由识别到的图标框推算（不写死），以适应不同期数的布局微调。
8. **入口可能有领奖弹窗**：从公会点进协力讨伐时，**有时会先弹出领奖页面**，必须先**点空白处关闭**才能进首领列表。
   → 复用现有 `点击空白处关闭弹窗` 节点（OCR 提示文字 `点击空白处关闭弹窗` → 点击 (1236,48)）。
   **战斗结束后也可能有奖励弹窗**，同样处理。

## 四、识别方案

| 识别器 | 类型 | 职责 |
| --- | --- | --- |
| `GuildRaidBossAttr` | CustomRecognition | 首领列表页 4 个槽位 ROI 做**字形匹配** → 各首领属性 + **图标外接框**（`框中心 + (120,54)` 即进详情页的点击点）；识别失败返回 `unknown` |
| `GuildRaidEntries` | OCR | 读 `剩余挑战次数 x/3` |
| `GuildRaidPresetRows` | OCR | 选择预设弹窗内可见行的**预设名 + 文本框坐标** |
| `GuildRaidEnterEnabled` | TemplateMatch / ColorMatch | 判定 `入场` 是否可点（黄=可点 / 灰=禁用） |

字形匹配流程：模板二值化 → 归一化到 24×24 → 与 6 个字形模板取 IoU 最大者 → 低于阈值判为 `unknown`。

字形模板来源：英雄界面 → 帮助 → 「属性关系」图例（6 个属性字形与首领列表一致）。

## 五、配置 `assets/config/teams.json`

```json
{
  "teams": [
    { "name": "土远",     "element": "earth" },
    { "name": "暗近",     "element": "dark"  },
    { "name": "米可虚近", "element": "virtual" },
    { "name": "虚勇虚近", "element": "virtual" }
  ]
}
```

- `name`：游戏内**预设名**，用于在弹窗中 OCR 定位行；
- `element` ∈ `fire` / `water` / `earth` / `light` / `dark` / `virtual`；
- **数组顺序 = 优先级**（平局时优先靠前的队伍）；
- 红点（未配置完）的队伍请**不要写进配置**。

## 六、分配算法

**输入**：4 个 BOSS 属性、N 个队伍、K = 剩余次数（≤3）

**输出**：K 对 `(BOSS, 队伍)`，约束 **BOSS 互不相同、队伍互不相同**（一场一个 BOSS 一个队伍）

**打分**：

| 关系 | 分值 |
| --- | --- |
| 队伍克制 BOSS | 1.3 |
| 互不克制 | 1.0 |
| 队伍被 BOSS 克制 | 0.7 |

**目标（字典序）**：

1. 最大化「克制」对数；
2. 最大化「中性」对数（即最小化「被克」对数）；
3. 平局：优先使用配置中靠前的队伍。

规模很小（K ≤ 3），直接枚举组合即可，不需要复杂匹配算法。

## 七、执行编排

采用 **Python Agent 编排**（`GuildRaidOrchestrator`），pipeline 只保留参数化的通用子图。

```mermaid
flowchart TD
    A[GuildRaid 入口：导航到首领列表页<br/>含「关闭领奖弹窗」] --> B[RaidScan：读 4 个 BOSS 属性 + 剩余次数]
    B --> C[RaidPlan：计算 K 对分配]
    C --> D[循环每一对]
    D --> E[RaidSelectBoss：图标框中心 +(120,54) → 详情页]
    E --> F[RaidOpenPreset：点 ≡ 打开弹窗]
    F --> G[RaidFindPreset：OCR 可见行<br/>未命中则上滑，最多 N 次]
    G -->|命中| H[点该名字文本框中心 → 弹窗关闭]
    G -->|未命中| I[跳过该队伍 → 重算剩余配对]
    H --> J{入场 是否可点}
    J -->|可点| K[RaidEnter → RaidAutoBattle → RaidWaitResult<br/>→ RaidExit → 关闭可能的奖励弹窗]
    J -->|禁用| I
    K --> D
    I --> D
    D -->|次数用尽 / 无法再分配| L[结束]
```

## 八、异常与兜底

| 情况 | 处理 |
| --- | --- |
| BOSS 属性识别失败（`unknown`） | 该 BOSS 排除出配对 + 日志告警 |
| 预设名在弹窗中 OCR 匹配不到 | 跳过该队伍，用剩余队伍继续 |
| `入场` 禁用（队伍英雄今日已用） | 跳过该队伍，剩余配对重算 |
| 入场后战斗异常 / 超时 | 回首领列表 → 重读剩余次数 → 继续 |
| 剩余次数为 0 | 直接结束 |
| 入口/结算出现领奖弹窗 | 先「点空白处关闭」再继续后续步骤 |
| 首领列表页读数失败 | 中止并提示，不做盲目点击 |
